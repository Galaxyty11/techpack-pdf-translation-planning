审计结论

值得保留

它已经验证了“原页旁注”这条路线

目标格式采用红色 FreeText，并实现页面分类、文字提取、OCR、批量翻译和空间搜索。作为概念验证，它比“全文替换式 PDF 翻译器”更贴近本项目。

不能直接上线

缺少业务闭环和失败边界

没有术语表、服装选择规则、逐项审核、结构化响应、可靠重试、审计记录和最终重叠校验。API 或排版失败时可能静默产出不完整文件。

最关键判断：不要在这一个脚本上继续堆判断。保留有价值的算法思路，但将未来实现拆为解析、规则、翻译、审核、坐标写入和质量门禁六个明确模块。

可取之处

目标格式

FreeText 方向与新需求一致

脚本使用 PyMuPDF 创建红色 FreeText，而不是直接替换英文内容。这为“保留原文、允许业务员后改”提供了正确基础。

多模态

按页面类型采用不同策略

存在 table_spec、table、drawing、text 等类型，并尝试用视觉模型辅助分类，比所有页面走同一套规则更合理。

效率

批量翻译和完全相同文本去重

先收集候选文本，再批量请求翻译并复用完全相同的结果，能减少重复调用和成本，适合保留为更严格缓存系统的起点。

扫描页

OCR 结果带坐标

技术图场景会对较大的图片区域使用 OCR，并尝试把坐标映射回页面，为处理嵌入图片中的英文提供了可验证思路。

排版意识

存在空间检测与候选位置搜索

SpaceDetector 会考虑页面内容区域和可用空间，并针对不同页面类型设置放置方式，说明作者意识到了“翻译正确但遮挡原文”仍然不可用。

工程基础

模式与参数已有雏形

SKILL.md 定义 translate/preview 模式，脚本暴露输入输出、模型和字体等参数，API key 缺失时也有显式提示；Python 源码通过语法解析。

现有脚本流程

1. 初始化检查依赖、API key、模型与字体
2. 页面分类文本特征 + 页面图片交给模型判断类型
3. 提取候选合并文字块；drawing 页补充图片 OCR
4. 批量翻译去重、分批请求 DashScope 兼容接口
5. 写入 PDF搜索空白区域并添加红色 FreeText

流程在“写入 PDF”后直接结束，缺少审核、写入后渲染、文字重叠检测、自动重排和无法解决时的交付阻断。

问题与风险

01
P0

没有术语表输入

  • 核心行业术语依赖硬编码提示和少量示例，不能读取业务员的 XLSX/CSV。
  • 没有最长匹配、别名、禁译项、优先级、上下文或冲突处理。
  • 同一术语跨页面的一致性没有可审计保证。
02
P0

翻译范围会明显过宽

  • 提示词倾向翻译表头、产品描述和工艺文字，但样本显示 General Information、How To Measure、Category Fields 和大量行政字段应跳过。
  • 规则不是基于 TechPack 页面类型、字段角色与服装术语的确定性组合。
  • Sample Review 没有“忠实提炼可执行结论”的专用策略。
03
P0

preview 不是无成本、无副作用的真正预览

  • 预览流程仍会初始化 API key，并可能调用页面分类或 OCR 模型。
  • 输出主要是前若干条文字，不是带页码、bbox、决策原因和风险的完整审核清单。
  • 用户无法逐项批准、修改、跳过或导出可重放的审核结果。
04
P0

模型响应缺少稳定的项目 ID

  • 批量翻译依赖行顺序对齐；模型合并、拆分或漏行时，译文可能对应错误原文。
  • 没有 JSON Schema、响应验证和数量/ID 完整性检查。
  • 异常路径可能返回空译文并继续生成“看似成功”的部分结果。
05
P0

没有最终重叠检测闭环

  • 写入前的启发式空白搜索不能证明实际 FreeText 字形不压到原文、表格线、图片或其他批注。
  • 紧凑兜底位置本身允许重叠风险，且写入后未重新渲染检查。
  • 没有最多 10 轮重排、页边引线兜底或 unresolved_overlap 交付阻断。
06
P0

缺少失败治理和审计

  • 没有指数退避、限流、断点续跑、持久缓存或明确的失败阈值。
  • 没有输入哈希、术语表哈希、模型版本、提示词版本和逐项决策记录。
  • 无法证明最终 PDF 只包含已经审核的译文。
07
P1

表格文本合并参数存在不一致

  • 函数说明指出 table 场景应使用更小的 merge_gap_factor，主流程对 table 调用时却沿用默认值。
  • 这会提高跨单元格、跨列或跨行合并的风险，导致原文和坐标失真。
  • 版面检测没有把矢量表格线作为一等约束。
08
P1

页面分类及 OCR 覆盖不完整

  • 分类 fallback 无法产生全部主流程支持的页面类型，例如 table_spec。
  • drawing 页只对较大图片块 OCR，可能漏掉小标签图、局部截图或被拆分的技术标注。
  • MinerU 等结构输出与 PyMuPDF 原始坐标没有双向校验。
09
P1

版面算法仍可能遮挡或裁字

  • 主要根据字符数估计所需尺寸，而不是用真实字体度量和最终 appearance stream。
  • table 模式的背景处理变量与实际写入行为不一致，白底可能遮住原内容。
  • 默认字号和目标框没有经过渲染验收，页面边界、旋转页和 CropBox 情况缺少覆盖。
10
P1

平台、依赖和输出约定不一致

  • 文档示例使用 python3、2>/dev/null 和 Unix 环境变量写法，却宣称跨平台；Windows 业务环境会踩坑。
  • 预检查涉及 dashscope，依赖章节却没有完整列出。
  • 默认输出在当前工作目录，而不是输入文件旁或明确任务目录。
11
P0

商业资料隐私未被说明

  • 页面图片、OCR 文本或整段内容可能发送到 DashScope。
  • 没有最小区域上传、数据分类、日志脱敏、留存策略和用户提示。
  • 模型与供应商硬编码，无法通过适配器执行企业级配置。
12
P2

缺少测试与干净的 skill 包结构

  • 没有单元测试、金样 PDF、不同阅读器兼容测试或真实 TechPack 回归集。
  • 压缩包包含 __MACOSX、__pycache__ 和 .pyc 等不应发布的文件。
  • 没有面向 Codex UI 的 agents 元数据、版本和明确兼容性说明。

建议复用边界

保留设计思想
- PyMuPDF FreeText 写入方向 - 页面类型分流 - OCR 坐标回映 - 完全相同文本去重 - 候选空白区域搜索 - preview / translate 两阶段概念
重新设计实现
- 术语与行业规则引擎 - 结构化翻译任务协议 - review.html / review.json 审核闭环 - MinerU 与原 PDF 坐标匹配 - 渲染级碰撞检测与自动重排 - 错误、缓存、审计、隐私和测试体系

最终建议：把上传 skill 视为“可运行的概念原型”和算法参考，而不是未来 skill 的代码底座。这样既能保留其正确方向，也不会让核心业务规则继续被埋在单文件启发式逻辑中。
