但没有一个能直接替代业务员

本页比较 GitHub 项目与 SkillsHub 技能，重点不是“谁能全文翻译”，而是谁能支持服装规则、术语强约束、保留英文、红色 FreeText、人工审核和无重叠交付。

推荐 组合底座，而不是采用全文翻译产品

用 MinerU 理解阅读顺序、表格与 OCR 结构；用 PyMuPDF 复核原始坐标、渲染页面并写入红色 FreeText。服装翻译规则、术语约束、审核页和重叠闭环需要自行设计。

分类结论

可直接使用：无。现成产品不同时满足六项核心条件。

可作为底层组件：MinerU、PyMuPDF；BabelDOC 可参考其术语和段落翻译机制。

不作为 v1 主链：PDFMathTranslate、Docling、Marker、PyMuPDF4LLM 和通用 SkillsHub 技能。

不是“能翻译 PDF”就算适配

评价分数为本项目内部适配判断，不代表通用产品排名。5 分表示接近当前需求，1 分表示需要大量重构。

01 行业选择能否只翻译工厂真正需要的内容
02 术语强约束能否锁定术语、代码、数字和单位
03 原文保留不覆盖、不替换原英文内容
04 批注对象能否生成红色、可编辑 FreeText
05 审核闭环逐项确认后才能写入 PDF
06 安全排版检测文字重叠并自动重排

逐项评估

PDFMathTranslate

参考架构全文翻译
  • 优点：项目成熟度高，入口完整，强调保持公式、图表和布局；支持页范围、例外规则、自定义提示和多翻译服务。
  • 不足：目标是科学文档全文翻译，产物不是原文旁的可编辑 FreeText；没有服装页面/字段规则和审核闭环。
适合学习布局保持、缓存和服务适配，不适合直接改成 TechPack 批注器。

BabelDOC

可借鉴CSV 术语表
  • 优点：文档翻译内核，支持 glossary 命中后注入提示，并提供扫描页与兼容性选项。
  • 不足：CLI 官方定位偏调试，主要仍是段落/全文翻译；实验性表格翻译和覆盖原文的 OCR workaround 不符合本项目原文保护要求。
可参考术语选择和翻译任务编排，但不能直接承担坐标批注层。

MinerU

推荐组件结构层
  • 优点：针对复杂文档输出 Markdown/JSON，支持多语言 OCR、表格、图片及跨页结构，适合识别 TechPack 的语义区域。
  • 不足：结构化输出不等于原 PDF 的最终批注坐标；它也不做翻译和 FreeText 写入。
只承担“读懂页面”，所有写入坐标仍由 PyMuPDF 复核。

PyMuPDF

推荐组件FreeText
  • 优点：可提取 bbox、图片、绘图和表格，渲染页面，并原生读写 FreeText 等批注。
  • 不足：没有业务语义、翻译、术语审核和自动排版策略；AGPL/商业许可需要正式评估。
作为原 PDF 的唯一坐标真相源和最终写入层，避免结构解析结果直接改页。

Docling / Marker / PyMuPDF4LLM

备选解析器
  • 共同优点：都能把复杂 PDF 转为结构化文本，支持不同程度的布局、表格和 OCR。
  • 共同不足：目标是内容提取而非原页旁注，坐标回写、业务选择和审核必须另建。
  • 选型差异：Docling 许可更宽松；Marker 部署更重且商业授权复杂；PyMuPDF4LLM 轻量但与 PyMuPDF 授权绑定。
保留为基准测试候选，不在 v1 同时引入，避免重复解析链。

SkillsHub 通用技能

不可直接用工作流说明
  • OpenAI PDF skill 强调渲染与视觉验收，但没有翻译业务逻辑。
  • Azure Document Translation skill 支持格式和 glossary，但面向云端整文档翻译，需要 Azure 存储。
  • Docling/Markdown 类 skills 主要包装现有解析工具，没有解决服装规则与 FreeText 写回。
可作为操作规范或组件入口，不能当作现成的服装翻译批注 skill。
